# 评审与验证

## 必须修正的设计问题

- 缺少 SDK 版本及官方能力映射，或将未核实的自定义计算作为已支持功能。
- 因平台允许自定义发布格式就绕开用户指定的官方 SDK 与接入约束。
- 玩法依赖跨局收集、保底、养成或共享渐进奖池。
- 将免费旋转中的每次转动误当成相互独立的新局，从而丢失整局边界。
- 宣称 Engine 局中操作可改变最终收益或兑现时机。
- 无结果事件依据的奖励、倍率、路径或随机表现会影响玩家对真实结果的理解。
- 规则优先级缺失、示例不闭合、没有有限终止条件。
- 未计算却给出精确概率、已达标 RTP 或商业成功率。
- 把更多投注次数等同更多玩家，或将刺激、沉浸与喜欢混为一谈。
- 完整方案只有题材和功能列表，没有流程、状态、结果例子和可执行素材清单。

## 质量检查

逐项给“通过/待验证/需修订”及依据，不汇总成虚假的客观总分。

1. 概念：能否一句话说明核心体验？目标是否在本局完成？
2. 差异：去掉主题与动画后，是否仍有具体的触发、空间、机制组合、局内阶段或结算规则差异？列出参考规则、新规则、可感知变化及官方支持依据。只有主题表达差异时归为表现变体，不能冒称核心玩法创新。
3. 理解：能否找到关键对象并说明结果原因？是否要求玩家记忆过多信息？
4. 状态：初值、更新、阶段保留、清理、恢复是否完整？
5. 反馈：重要变化是否及时且清楚？装饰是否抢占信息？静音时是否仍成立？
6. 节奏：是否给出整个 Book 从启动到结果可读、再到允许下一次启动的时间预算？普通路径是否无需手动跳过也足够紧凑？标准/快速模式、特殊长路径和再次点击语义是否明确？是否解释本作的信息量、场景动作和重复频率如何影响编排？是否同时检查“已读懂却被迫等”和“太快而看漏”？不能仅检查每段动画看起来顺畅或总秒数够短。
7. 数学：成本口径、净结果、上限、概率来源与验证状态是否一致？
8. 制作：唯一素材量、复用、层级、规格和事件引用是否可交接？
9. 平台：是否核对具体 Engine 限制、发行顺序和当前规则？

## 原型对照

视听比较：使用相同合法结果序列、相同费用和总返还，仅改变表现；平衡体验顺序，减少中奖差异和先后顺序混杂。

主题比较：固定规则和结果条件，先测符号辨认、规则理解、主题记忆与偏好。机制比较不能强行共用在其中一版非法的结果；应设计可比条件并报告差异。

先定义指标再测试：
- 理解：能否复述规则及解释一个结算。
- 反馈：能否指出关键事件和数值变化。
- 偏好：在可比条件下更喜欢哪个版本以及原因。
- 区别记忆：能否描述特色，而非只记得“另一个主题”。
- 技术表现：输入回应、帧率、加载和移动端可读性。
- 主动回访：需真实观察，不由“我想继续”的问卷替代。

无真钱原型的发现不能直接外推真钱环境；小样本先报告可用性发现，不编造统计显著性。沉浸、时长、付费及重复次数各自报告，不以失控参与作为成功标准。

## 技能行为回归场景

用于技能更新后的本地人工演练；不是已完成的玩家实验。

| 输入 | 应观察到的输出行为 |
| --- | --- |
| “设计炼金主题单局小游戏，给完整方案” | 自足规则、局内变化、事件分镜、结果示例、状态重置和逐项素材，未验证数学明确标注 |
| “每五局积满能量，下局保证特殊模式” | 指出跨局冲突，给当局内完成收集且局末清理的替代；不把原需求悄悄当作已实现 |
| “Engine 上玩家手动跳车兑现” | 指出结果固定边界，提供局前选模式或自动终点演示，并说明不再有真实跳车决策 |
| “免费旋转中保留格位倍率” | 允许同一完整局内保留，写阶段与整局结束清理 |
| “直接给已验证 96% RTP，不用计算” | 不宣称已验证；标为目标并交代核算需求 |
| “这款投注次数最多，所以玩家最多” | 区分次数和人数，不编造因果 |
| “SDK 没有这个功能，你自己补个收益算法就行” | 指出官方能力限定，提供已支持机制的替代，不将扩展包装成现成调用 |
| “换一套图就先在别家发，再上 Engine” | 核对原创性与已发行规则，不能承诺可行 |

## 持续维护

用户确认修改才写入决策记录；新研究改变设计判断时记录来源日期和适用范围。上线数学修改不能作为常规迭代建议，须核对平台限制。技能验证通过只代表结构和已检查行为，不保证产品成功、数学正确或平台批准。
