# 策划技能决策记录

仅记录用户明确确认的选择。助手建议、研究假设与未核实平台陈述分别保留。

## 用户已确认（2026-11-23）

| 决策 | 对技能的影响 |
| --- | --- |
| 深入研究 Stake 类小游戏底层机制 | 核心为研究、玩法设计与原创延展 |
| 核心玩法搭配不同场景产生创新 | 说明主题如何参与规则与体验，区分换皮和机制变化 |
| 关注即时反馈、爽点和重复游玩吸引力 | 输出局内事件与反馈要求，分别验证理解、偏好和继续意愿 |
| 最终交付完整游戏策划方案，包括场景、玩法、素材清单 | 方案可供开发、美术、音频和测试交接 |
| 可面向其他平台，也可供 Stake 使用 | 核对平台与发行顺序，不擅自限定为非真钱产品 |
| 必须单局、无状态 | 禁止影响下一局的玩法进度，允许明确边界内的局内变化 |
| 严格使用 Stake 官方 SDK 与接入能力 | 每个机制须有官方能力映射；优先复用与配置，未确认支持的扩展不进入可执行方案 |
| 在 SDK 和平台约束范围内做出玩法创新是首要目标 | 场景服务于规则创新；只换主题或反馈不能作为核心玩法差异，需说明去掉包装后的具体改变 |
| 先讨论调研，再形成完善技能 | 当前为研究驱动 v1，持续通过实际方案验证 |

## 已撤销的助手假设

- “用户只要非真钱、不可兑换游戏”：用户未确认，后续明确支持 Stake 使用。
- “必须加入成长、收集、每日目标或长期留存系统”：与单局约束不符。
- “核心体验必须通过玩家技能或中途撤离形成”：不符合 Engine 已核对的固定结果模型。
- “单局固定为 10–60 秒”：未确认，按具体机制与测试决定。

## 已核对的平台事实

见 platform-boundaries.md。事实核对日期与用户决策日期独立，不把平台资料当作用户偏好。

## 未核实的判断

“多数玩家只喜欢高波动”“使用成熟模板更易过审”“几千款及特定工作室表现评价”需要各自证据。无状态约束不能独自解释同质化。

## 待具体项目确定

主题、参考版本、设备、目标地区、预算、交付格式、模式、数学目标、发行顺序。不得无依据补成已确认要求。
